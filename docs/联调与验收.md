# 三端协同链路联调与现场验收边界

## 1. 启动可复测版本

```bash
pip install -r requirements.txt
python scripts/run_stack.py
```

- 小车监控：http://127.0.0.1:8001
- 云端监控：http://127.0.0.1:8002
- 护工服务：http://127.0.0.1:8003
- 三端默认共享仓库 `runtime/collaboration.sqlite3`。启动器仅监听回环地址。
- `SILVERGUARD_DB` 可指定同一台主机上的绝对数据库路径。不要把 SQLite 文件放到 SMB/NFS 上，也不要把本实现视为跨主机云边同步服务；跨主机仍须部署统一网关及鉴权、离线队列。
- `SILVERGUARD_LEGACY=1` 仅用于查看原始独立 JSON 原型，不提供本次去重与闭环保证。三端不要混用两种模式。
- 数据库包含事件位置、处置身份，已被 Git 忽略；需限制本机文件访问权限并备份。原始演示缓存不自动导入新状态库。

Web 前端从服务根路径打开，默认同源请求。微信开发者工具打开 `src/护工移动端`，将 `config/api.js` 的 HTTP/WS 地址分别设为 `http://127.0.0.1:8003`、`ws://127.0.0.1:8003`，配置护工身份。真机的 `127.0.0.1` 指手机自身，真机联调需另行部署受控 LAN/HTTPS 网关及合法域名，不能直接使用上述地址。移动端“处理完成”仅在后端确认到场后成功，断网或服务拒绝不会只改本地状态并提示成功。

本次验证了 HTTP、跨进程 WebSocket 及移动端业务适配函数；没有操作微信开发者工具，也没有完成网页/小程序全页面视觉验收。地图、老人资料及现场媒体不由协同状态库提供，干净克隆可能为空。

## 2. 最小接口闭环

所有路径加 `/api/v1`，响应沿用 `{code:0,message:"ok",data:...}`。

| 步骤 | 方法与路径 | JSON 示例 |
| --- | --- | --- |
| 登记在线机器人 | `POST /robots/A/telemetry` | `{"battery":90,"online":true}` |
| 上报受控事件 | `POST /events` | `{"event_id":"evt-lab-001","run_id":"run-lab-001","type":"授权演练","position":"模拟走廊"}` |
| 查看同一任务 | `GET /tasks` | 三端任意服务均可查询 |
| 无车时重新尝试派单 | `POST /tasks/{task_id}/dispatch` | 无请求体 |
| 车端接单 | `PATCH /tasks/{task_id}` | `{"robot_id":"A","status":"已接单"}` |
| 车端到场 | 同上 | `{"robot_id":"A","status":"已到场"}` |
| 护工确认 | `POST /events/evt-lab-001/confirm` | `{"handled_by":"caregiver-test"}` |
| 抽查证据链 | `GET /events/evt-lab-001/trace` | 按顺序返回关联事件/任务的审计快照与 UTC 时间 |

同一事件重试必须保持 `event_id`、`run_id`、`type`、`position` 一致，重复请求返回原任务；修改关键内容返回 409。发送方应持久化事件 ID，超时后按原 ID 重试，不得每次生成新 ID。`event_id` 不清理、不使用原版最多 100 条的截断方式去重。

事件及任务创建、派单、审计记录位于同一 SQLite 事务，唯一键与 `BEGIN IMMEDIATE` 保护多线程/多进程竞争。只选电量至少 20%、心跳在 30 秒内且无未结任务的机器人，按 ID 稳定选择。这是**软件联调调度基线，不是论文算法部署**，没有控制两台实体车。无人可用时保持待派单，需恢复心跳后显式重试派单；不凭“健康检查 200”认定车辆在线。

状态顺序：`待派单 → 已派单 → 已接单 → 已到场 → 已完成`；事件最终为 `已处理`，小程序适配显示为“已完成”。车端不能跳步或回退，回执须匹配分配的 robot_id。允许失败回执，但必须带 `reason`，失败仍保留记录，不能计为完成。失败后的机器人是否安全可复用必须人工核实；**当前软件状态机不替代实车锁车、急停或人工复位机制**。护工确认必须包含身份，但它是审计标签，不是经过认证的登录身份。

每个服务按持久审计序号轮询并广播增量（约 0.5 秒），重启后客户端通过 HTTP 拉取快照。数据库是恢复依据，WebSocket 不承诺端到端恰好一次投递；断连后应重新读取快照。车辆回执也可按同一状态重试。未结任务重启后不会重新生成派单；旧设备缓存中的任务不会迁移或自动恢复运动。

## 3. 自动验证

```bash
python -m pytest tests -q
python scripts/verify_stack.py
node tests/mobile-confirmation.cjs
```

- 单元/API 测试：并发 16 次上报、ID 冲突、状态跳步、错误车辆回执、离线/低电/过期心跳、忙碌预留、失败原因、重复回执、三端读写与终态恢复。
- 真实进程验证：临时目录复制三端，不使用原运行缓存；启动三个 Uvicorn 服务，验证重复上报只建一单、云端收到跨进程 WS、小车服务重启保留未结任务、护工确认后三端一致、护工服务重启保留终态。
- 移动端 Node 测试：未到场/断网时不伪造成功，成功回执后才写缓存。

这些测试的机器人身份与回执均为人工注入，**不是感知触发、车端协议、实车轨迹或养老院部署证据**。

## 4. 现场待办与记录

进入现场前必须确认：两台车的固件/底盘版本、边缘模型及校验值、地图、楼层和禁行区、统一时钟及偏差、网络与掉线策略、电量范围、速度/制动上限、物理急停、授权范围、联系人和原护理流程兜底。包内未发现可证明视频部署版本的完整车端归档，不能填成已具备。

使用 `docs/实测记录模板.csv` 每个阶段记录一行；另保存原始双车轨迹、视频索引、配置和版本清单。建议按原 TODO：先台架 8 小时，再争取养老院 72 小时/7 天；双车对照各至少 10 轮，并发告警、窄道、掉线各 3 轮。发生重复派单、非预期运动或碰撞立即停止试验。

任务完成率=完成数/总触发数，超时/失败不剔除；告警到接单、到场、补位、回归分别统计并保留最差值。可用率分母是约定服务窗口，计划外停机计入损失。演练、日常运行、故障注入分开统计。没有真实现场时明确写“实验室/模拟走廊”，不得填写养老院在线时长与可用率。
